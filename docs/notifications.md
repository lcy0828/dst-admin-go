# 邮箱与 Webhook 通知

入口：**系统设置 → 通知**。配置保存后立即生效。

通知由管理端统一发送。本机和已接入 Agent 的管理任务共用这些渠道；独立 Agent 无需配置邮箱。SMTP 和 Webhook 必须能从管理端所在的主机或容器访问。

## 配置邮箱

1. 展开 **邮件服务器（SMTP）**，填写服务器、端口、发件邮箱及按需填写的账号和密码，然后保存。常用端口为 `465`（TLS）或 `587`（STARTTLS）；不需要认证的内网邮件中继可以不填账号。
2. 点击 **测试 SMTP 连接**，检查连接、TLS 和认证。此测试不发送邮件。
3. **添加渠道 → 邮箱**，填写渠道名称、接收邮箱并选择事件。一个渠道最多 20 个接收邮箱，可每行填写一个。
4. 保存渠道，点击 **测试发送**。在发送记录中查看实际邮件发送结果。

`已被接收` 表示邮件服务器接受了邮件；请同时检查收件箱与垃圾邮件。SMTP 设置未保存时，渠道发送仍使用之前保存的配置。

## 配置 Webhook

1. **添加渠道 → Webhook**，填写名称、地址和接收事件。
2. 通用接口可以直接使用默认 JSON。企业微信、钉钉、飞书机器人在 **请求与消息模板** 中选择对应预设，再填写机器人提供的 Webhook 地址。
3. 自定义接口可选择 `POST` / `PUT`、JSON / 纯文本，以及自定义请求头和消息模板。
4. 保存后 **测试发送**，查看发送记录中的结果。机器人预设同时检查接口返回的业务状态码。

自定义请求头示例：

```json
{
  "Authorization": "Bearer YOUR_TOKEN"
}
```

Webhook 地址及请求头保存后不再返回明文。编辑时留空保留原值；请求头填 `{}` 清除。需动态签名的机器人验证方式暂不支持，可使用接受固定令牌的接收接口或自行部署转发服务。

## 事件与筛选

| 页面选项 | 触发时机 |
| --- | --- |
| 房间启停结果 | 面板房间启动、停止、重启等管理任务结束，包括部分失败 |
| 备份与恢复结果 | 手动或定时备份、恢复、备份清理任务结束 |
| 游戏安装与更新结果 | 本机或 Agent 的游戏安装、接入已有安装、更新任务结束 |
| 模组操作结果 | 模组管理任务结束；成功的日常更新检查不发送 |
| Agent 离线与重新连接 | 已观测 Agent 的连接状态发生变化；首次观测和管理端重启不群发状态通知 |
| 登录失败触发限制 | 连续登录失败达到限制阈值 |
| 发现管理服务新版 | 后台或手动检查发现新版；同一渠道对同一组件、节点和版本去重 |
| 发现 Agent 新版 | 后台检查发现已登记 Agent 存在可用新版 |
| 自定义消息 | 在通知页手动发送，或调用自定义通知 API |

每个渠道可以单独启停、选择事件。**仅发送失败或异常** 会过滤成功、恢复在线和自定义消息，新版提醒与测试发送不受此筛选影响。无人更新任务没有实际更新时不发送成功通知。

通知只转发任务类型、状态、房间/世界标识、任务 ID 和错误代码，不转发原始命令输出或任意日志。任务通知属于管理操作结果，暂不包含独立的游戏进程崩溃检测或玩家进出通知。

## 自定义消息模板

将变量写成双花括号，例如 `{{title}}`。JSON 模板中的变量需放在字符串值中，系统自动处理消息中的引号与换行。

```json
{
  "text": "{{title}}\n{{message}}",
  "event_id": "{{id}}",
  "room": "{{roomId}}"
}
```

| 变量 | 内容 |
| --- | --- |
| `id` | 事件唯一标识，可用于接收端去重 |
| `event` | 事件类型，如 `backup.result` |
| `title` / `message` | 标题 / 正文 |
| `status` | 任务或事件状态 |
| `roomId` / `targetId` / `jobId` | 可用时的房间 / 节点 / 任务标识 |
| `timestamp` | UTC 事件时间 |

**发送自定义消息** 会发送到启用且订阅自定义消息的渠道。API 为 `POST /api/v2/system/notifications/actions/send`，遵循现有登录、CSRF 和幂等请求要求，详细接口见 [OpenAPI](openapi-v2.yaml)。

## 发送记录与数据保留

发送在后台串行处理，不阻塞游戏任务。没有待发送消息时，发送器休眠；页面仅在当前列表存在待发送消息时刷新结果。

Webhook 连接失败、HTTP `429` 或 `5xx` 最多自动尝试 3 次；自动重试沿用 `X-DST-Event-ID`，接收端可据此去重。邮件不自动重发。管理端重启中断的发送标为失败，可手动 **重新发送**；对方可能已经接收，重发可能重复。

最多保存 32 个渠道、1000 条待发送记录和最近 2000 条完成记录。删除渠道保留历史，并取消尚未开始的发送；已在发送的请求可能完成。

备份管理数据时，保留数据库及配置目录中的 `notifications/webhook.key`。密钥丢失会导致原 Webhook 凭据不可读；恢复匹配的密钥，或重新填写每个渠道的地址和全部请求头（没有请求头则填 `{}`）。SMTP 凭据按现有系统配置方式保存。

## 软件新版提醒

在通知渠道中订阅“发现管理服务新版”或“发现 Agent 新版”。新版提醒不会被“仅发送失败或异常”过滤。

通知设置中的“后台检查软件新版”默认开启，每 30 分钟检查一次，可以关闭或改为 30～10080 分钟（最多 7 天）。已有保存的检查间隔继续生效。只有存在已启用的新版订阅时才会定期访问发布源；无需保持浏览器打开，也不会启动或查询游戏世界。管理服务使用软件更新页保存的下载源和网络代理。Agent 新版检查使用控制端已登记的版本信息，不要求每个 Agent 单独访问 GitHub。

同一渠道对同一组件、节点和版本只入队一次，重启和清理发送历史不会重置记录。投递失败可在发送记录中查看和重试；中断的投递可能已经到达收件方，手动重试可能重复发送。

仅连接 MCP 不会创建通知订阅。若 AI 机器人支持接收 Webhook，可为它添加 Webhook 渠道并订阅新版事件；机器人收到通知后再通过 MCP 查询版本详情或执行用户要求的更新。当前 MCP 使用请求响应方式，没有主动推送新版事件的订阅接口。此通知目前覆盖管理服务与 Agent，游戏服务端和 LuaJIT2 新版尚未接入同一提醒机制。
