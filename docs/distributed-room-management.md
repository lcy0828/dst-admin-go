# 多机器房间管理

单机直接使用内置 Runtime。有远程机器时，按[启动指南](startup-guide.md#接入远程-agent)添加 Agent；已有完整管理实例可以切换为“加入管理中心”，使用内嵌 Member。不要让 Agent 和另一个管理实例同时控制同一存档目录。

## 基本概念

| 对象 | 含义 |
| --- | --- |
| Room | 一个 DST Cluster，拥有 Token、公共配置和多个世界 |
| World / Shard | Master、Caves 或其他世界，Master 是唯一主分片角色 |
| Runtime | 运行游戏的本机、远程 Agent 或受管容器环境 |
| Installation | 目标机器登记的游戏和存档目录 |
| Placement | 世界实际使用的 Runtime 和 Installation |

一个房间可以跨机器放置世界。选择目标后先检查实际目录、安装状态、端口和 Master 的可达地址。页面中的本机路径是所选机器的路径；容器必须先挂载相应目录。

## 创建、迁移和操作

1. 登记目标 Runtime，确认在线且能力满足要求。
2. 在“游戏服务端管理”中安装游戏或接入已有目录。
3. 创建房间和世界，规划目标位置并检查预览。
4. 执行部署或迁移，等待逐世界结果；新房间配置下发不等于传输现有游戏 Session 存档。
5. 启动并确认游戏日志、分片互联和玩家连接。

已有世界换机器请使用迁移流程，保留源恢复点。操作依据当前生效 Placement，目标离线不会退回控制端本机执行。房间级操作可能部分成功；查看逐世界状态和可恢复操作，不要把 Job 结束直接当作全部成功。

## 模组与配置

游戏文件和模组文件属于目标节点；同一模组可以在不同房间、世界使用不同配置。下载、启用和重启是不同动作。配置保存会检查版本冲突，避免覆盖页面打开后发生的手工修改。普通启动不会重新发布所有配置或模组。

## 备份与恢复

完整房间备份包含公共文件以及所有必要分片的快照和校验信息。跨机器只备份控制端目录不能得到完整房间备份。仅完整且通过校验的备份集适合默认恢复；部分备份不能当作完整恢复点。

热备份要求各分片提供一致的保存屏障证据；无法满足时使用协调停服后的冷备份。恢复前停止房间、检查目标、创建保护备份，再分发并校验所有分片。中断后查看持久操作记录，按页面提供的恢复流程处理。

另行备份控制端数据库、配置以及 Agent 身份和操作状态；这些平台状态与游戏存档用途不同。不要通过删除状态文件、owner lock 或存档来解除冲突。

## 容量和平台边界

2C4G 优先一个 Master+Caves 房间，CPU 建议统计同机全部运行世界；内存独立预检。跨机部署还需要正确的 UDP 和分片通信地址。

独立世界容器与 All-in-One 是不同模型，见[部署模型](deployment-profiles.md)。Kubernetes 目前仅提供实验性的观察和预检，不能用于生产控制世界生命周期。
