# 多房间名单与社区共享封禁方案

> 状态：设计草案，当前不实施
> 更新日期：2026-08-15
> 适用范围：DST Admin 本地房间名单管理，以及未来可选的社区举报与共享黑名单服务

## 1. 背景

DST 原生将访问名单保存在 Cluster 根目录：

```text
<save-root>/<room-directory>/
  adminlist.txt
  blocklist.txt
  whitelist.txt
  Master/
  Caves/
```

因此同一房间的地面和洞穴共享名单，不同房间各自独立。当前系统的“房间特殊名单”、独立“特殊名单”页面和房间列表弹窗都操作同一份房间级文件。

玩家管理页面执行封禁时，还会在本地数据库记录房间、玩家、原因、期限和到期时间；直接编辑特殊名单只修改 DST 文件，不具备完整的来源、原因、期限和审计信息。

未来需要同时覆盖：

1. 一个服务器安装中，多个房间可以按需共享部分名单。
2. 房间仍能保留自己的独立名单和例外。
3. 本地系统在没有中央服务时完整可用。
4. 用户可选择提交带证据的玩家举报。
5. 中央审核服务可发布可验证、可撤销、可申诉的共享黑名单。

## 2. 设计原则

- 本地优先：不配置社区服务时，房间、玩家和名单功能不受影响。
- 显式订阅：任何跨房间或社区名单都不能默认启用。
- 权限隔离：管理员名单不允许通过社区服务分发，也不允许隐式跨房间共享。
- 最小执行：共享黑名单默认只提示，不默认自动封禁。
- 来源可见：每条生效记录必须能解释由谁、从哪里、因为什么产生。
- 可逆：支持豁免、过期、撤销、回滚和恢复上一个可信版本。
- 原生兼容：最终仍生成 DST 可直接读取的三个名单文件。
- 防误封：举报数量不能直接等价为违规事实或封禁决定。
- 最小证据：默认只上传相关时间窗口的日志片段，不上传整个存档或全部日志。

## 3. 范围与术语

### 3.1 名单作用域

| 作用域 | 含义 | 默认行为 |
| --- | --- | --- |
| 房间本地 | 只影响一个房间 | 保持现有行为 |
| 名单策略组 | 由同一安装中的多个房间显式绑定 | 不自动绑定 |
| 安装级 | 当前 DST Admin 安装中的全局本地策略 | 默认关闭 |
| 社区订阅 | 从可选审核服务获取的签名名单 | 默认只观察 |
| 房间豁免 | 对指定共享来源的例外 | 只影响对应来源 |

“服务器”在界面上容易同时指运行节点、DST 安装和房间。新增界面应使用明确名称：`当前安装`、`房间`、`名单策略组`、`社区订阅`。

### 3.2 名单类型

- 管理员名单：授予管理权限，风险最高。
- 黑名单：拒绝指定 KU ID 进入房间。
- 白名单：在启用白名单模式时允许指定 KU ID 进入房间。

三种名单必须分别建模，不能共用一个模糊的“特殊用户”权限标记。

## 4. 本地多房间共享

### 4.1 名单策略组

新增“名单策略组（Access Profile）”。用户可以创建一个策略组，并选择哪些房间使用它。

建议默认规则：

- 黑名单可以通过策略组共享。
- 白名单只能由用户显式创建和绑定策略组。
- 管理员名单只能在本地显式共享，绑定时需要高风险确认；不得自动传播。
- 新建房间不自动继承任何策略组，创建向导可以让用户主动选择。
- 修改记录时必须明确选择“仅当前房间”或“所属策略组”，不能静默影响其他房间。

不使用符号链接，也不让多个房间直接编辑同一个 `blocklist.txt`。符号链接会破坏当前安全路径校验、备份边界、原子写入和房间删除语义。

### 4.2 建议数据模型

| 对象 | 关键字段 | 用途 |
| --- | --- | --- |
| `access_profile` | `id`、`name`、`description`、`created_at` | 名单策略组 |
| `access_profile_entry` | `profile_id`、`list_type`、`user_id`、`reason`、`expires_at` | 策略组条目 |
| `room_access_binding` | `room_id`、`profile_id`、`list_type`、`enabled` | 房间绑定关系 |
| `room_access_entry` | `room_id`、`list_type`、`user_id`、`reason`、`expires_at` | 房间本地条目 |
| `room_access_exemption` | `room_id`、`source_type`、`source_id`、`user_id`、`expires_at` | 对特定共享来源的豁免 |
| `access_materialization` | `room_id`、`revision`、`file_hashes`、`materialized_at` | 最终文件同步状态 |
| `access_audit_event` | `actor`、`action`、`target`、`before`、`after`、`created_at` | 审计与回滚依据 |

现有 `player_ban` 可以继续记录玩家管理产生的封禁，但需要增加统一来源映射，避免它与 `room_access_entry` 形成两套互不解释的数据。

### 4.3 合并与优先级

黑名单建议按以下规则生成：

```text
最终黑名单 =
    房间本地明确封禁
  + 未过期的玩家管理封禁
  + 已绑定策略组中的封禁
  + 已接受的社区封禁（扣除仅针对社区来源的房间豁免）
```

关键约束：

- 房间本地明确封禁优先级最高。
- 社区名单豁免只能抵消指定社区决定，不能解除房间本地封禁。
- 策略组豁免必须指向具体策略组和条目，不能用全局减法掩盖冲突。
- 同一 KU ID 来自多个来源时，界面合并展示，但保留全部来源。
- 只有全部有效封禁来源都失效或被对应豁免后，KU ID 才从最终文件移除。

管理员和白名单使用各自独立的合并规则，不受社区黑名单订阅影响。

### 4.4 运行时物化

数据库保存期望状态、来源、期限和审计；DST 原生文件是运行时物化结果：

```text
策略变化
  -> 计算房间有效名单
  -> 生成预览和冲突说明
  -> 创建保护备份
  -> 原子写入三个原生文件
  -> 记录 revision、hash 和审计事件
  -> 尝试应用支持的实时命令
```

实时行为需要明确区分：

- 黑名单变更：运行中分片可发送 `TheNet:Ban()` 或 `TheNet:Unban()`，失败时保留文件结果并展示警告。
- 管理员和白名单：只有确认 DST 支持可靠热更新时才实时应用，否则标记“重启房间后生效”。
- 多分片：按房间统一物化文件，但运行时命令需要覆盖所有必要分片并记录每个目标结果。

### 4.5 外部修改与漂移

用户仍可能手工修改名单文件。系统必须检测文件 hash 与最近物化记录是否一致：

- 没有漂移：正常写入。
- 有漂移：禁止静默覆盖，展示差异。
- 用户可选择把外部新增项导入为房间本地条目。
- 用户可选择用系统期望状态覆盖，但必须先备份并确认。
- 不允许自动把外部管理员名单传播到策略组。

## 5. 社区举报与审核服务

### 5.1 部署边界

社区审核服务应与开源本地核心分离：

- 本地核心负责举报整理、脱敏、上传授权、订阅验证和名单物化。
- 中央服务负责证据接收、去重、自动分析、人工审核、申诉、撤销和签名发布。
- 中央服务不可用时，本地管理功能继续工作。
- 本地最多继续使用最后一个未过期且签名有效的可信快照。

### 5.2 举报流程

```text
选择玩家和行为类型
  -> 选择事件时间范围
  -> 本地抽取相关日志片段
  -> 自动脱敏与敏感项检查
  -> 用户预览并确认上传
  -> 生成清单、hash 和实例签名
  -> 中央服务接收并返回举报 ID
  -> 自动分析和去重
  -> 人工审核或补充证据
  -> 发布决定、驳回或要求补充
```

举报必须以稳定 KU ID 为目标，显示名称只能作为辅助信息。

### 5.3 证据包

建议证据包仅包含：

- 目标 KU ID。
- 举报分类和用户填写的说明。
- 事件开始、结束时间。
- 房间和世界的非敏感元数据。
- 相关时间窗口内的服务端日志片段。
- 日志来源文件、偏移范围和 hash。
- DST 版本、解析器版本和证据格式版本。
- 证据清单 manifest。
- 本地实例公钥标识和签名。

默认禁止上传：

- `cluster_token.txt`、Steam API Key、登录 Token 和密码。
- 与事件无关的完整聊天记录。
- 无关玩家的 IP、平台标识和个人信息。
- 整个存档、Mod 文件或无限时间范围的日志。

上传前必须提供可读预览，并允许用户删除无关片段。中央服务需设置加密存储、访问审计和明确的证据保留期限。

实例签名只能证明证据由某个安装提交，不能证明服务器管理员没有伪造日志，自动审核不能把签名当作真实性证明。

### 5.4 自动分析

自动服务适合执行：

- 日志格式和 hash 完整性校验。
- 目标 KU ID 与会话时间关联检查。
- 重复举报、重复事件和重复证据检测。
- 已知行为模式识别和证据片段定位。
- 举报分类建议、证据质量评分和审核优先级排序。
- Token、IP 和无关个人信息的二次脱敏检测。

自动服务不应仅凭模型输出或规则得分直接发布永久封禁。

### 5.5 审核与反滥用

严禁使用“原始举报次数达到阈值即进入共享黑名单”。决定至少需要综合：

- 独立运营者数量，而不是账号或请求数量。
- 独立安装数量和安装历史。
- 是否为同一事件、同一证据或协同举报。
- 证据质量、完整性和可复核程度。
- 举报者历史准确率和恶意举报记录。
- 行为严重性、重复性和时间跨度。
- 目标玩家的申诉材料与历史撤销记录。

反滥用能力应包含：

- 实例注册与密钥轮换。
- 速率限制和配额。
- 事件、证据 hash、运营者和安装多维去重。
- 举报者信誉只用于排序，不能替代证据。
- 审核员利益冲突回避和操作审计。
- 高风险决定的双人复核。
- 对虚假举报者的降权、暂停和申诉机制。

### 5.6 决定状态

共享决定建议使用以下状态，而不是简单布尔黑名单：

| 状态 | 含义 | 本地默认动作 |
| --- | --- | --- |
| `observed` | 存在待观察风险 | 仅提示 |
| `warned` | 证据支持风险警告 | 进入时告警 |
| `blocked_temporarily` | 有期限的共享封禁 | 需要本地批准 |
| `blocked` | 高置信度封禁决定 | 需要本地批准 |
| `revoked` | 决定已撤销 | 从共享来源移除 |
| `expired` | 决定已到期 | 自动失效 |

每个决定必须包含：

- 稳定决定 ID 和目标 KU ID。
- 分类、公开理由和严重程度。
- 证据摘要，不直接公开敏感原始日志。
- 决定时间、生效时间和到期时间。
- 审核等级和置信度区间。
- 申诉入口。
- 替代决定和撤销关系。

### 5.7 签名名单发布

中央服务发布版本化、签名的快照或增量：

- 客户端内置或由管理员确认发布公钥。
- 下载后校验签名、版本、生成时间和有效期。
- 校验失败时拒绝使用，不能降级为未签名数据。
- 保存最后一个已验证版本，支持查看差异和回滚。
- 撤销信息优先于旧封禁决定。
- 中央服务回滚版本号或返回过期快照时必须告警。

初期优先使用定期签名快照，不引入复杂消息队列或强实时同步。共享黑名单不是秒级控制能力，稳定和可审计比实时性更重要。

## 6. 本地订阅模式

用户可以按房间或策略组选择：

| 模式 | 行为 | 建议 |
| --- | --- | --- |
| 仅观察 | 展示风险，不写入 `blocklist.txt` | 默认 |
| 本地批准 | 逐条或批量确认后执行 | 推荐 |
| 高置信度自动执行 | 满足本地阈值后自动物化 | 成熟阶段可选 |
| 关闭 | 不获取或不展示社区数据 | 始终支持 |

即使开启自动执行，也必须支持：

- 房间级豁免。
- 最大自动封禁期限。
- 只允许特定类别自动执行。
- 每次变更通知和审计。
- 一键恢复上一个已验证快照。
- 中央服务不可用时禁止基于过期新数据扩大封禁范围。

## 7. 界面建议

### 7.1 特殊名单

每条记录展示：

- KU ID 和已知玩家名称。
- 名单类型。
- 来源徽标：本房间、策略组、玩家封禁、社区名单、手工导入。
- 原因、创建者、生效时间和到期时间。
- 当前状态：已生效、待同步、需重启、已豁免、已过期、同步失败。

同一 KU ID 有多个来源时，以一行汇总，并提供“查看来源”详情，不重复占用列表空间。

### 7.2 策略组

- 展示绑定房间数量和影响范围。
- 修改前预览会影响哪些房间及文件。
- 管理员名单绑定使用单独的高风险确认。
- 删除策略组前展示失效条目，并允许转为房间本地记录。

### 7.3 举报

- 从玩家历史或日志事件发起，减少手工填写 KU ID。
- 先选择行为类型和时间窗口，再生成证据预览。
- 清楚显示将上传哪些内容以及保留期限。
- 举报提交后展示处理状态、补充证据请求和最终决定。

## 8. API 边界草案

本地 API 可按领域提供：

```text
GET    /access-profiles
POST   /access-profiles
GET    /access-profiles/{profileId}
PATCH  /access-profiles/{profileId}
POST   /rooms/{roomId}/access-profiles/{profileId}/actions/bind
POST   /rooms/{roomId}/access-profiles/{profileId}/actions/unbind
GET    /rooms/{roomId}/access/effective
POST   /rooms/{roomId}/access/preview
POST   /rooms/{roomId}/access/actions/materialize
GET    /rooms/{roomId}/access/drift
POST   /rooms/{roomId}/access/actions/import-drift

POST   /reports/drafts
POST   /reports/{reportId}/actions/build-evidence
POST   /reports/{reportId}/actions/submit
GET    /reports/{reportId}

GET    /community-blocklist/subscriptions
POST   /community-blocklist/subscriptions
GET    /community-blocklist/decisions/{decisionId}
POST   /community-blocklist/decisions/{decisionId}/actions/approve
POST   /community-blocklist/decisions/{decisionId}/actions/exempt
```

所有修改仍通过现有 Job 体系执行，并在终态刷新有效名单、文件状态、审计和订阅状态。

## 9. 分阶段路线

### Phase 1：本地名单统一

- 建立统一名单数据模型和来源追踪。
- 将直接名单编辑和玩家封禁收敛到同一服务。
- 实现房间有效名单预览、物化、漂移检测和审计。
- 保留现有文件兼容与保护备份。

完成标准：任意 `blocklist.txt` 条目都能解释来源；数据库与文件不一致时不会静默覆盖。

### Phase 2：本地多房间策略组

- 创建、绑定、解绑策略组。
- 实现来源级豁免和影响范围预览。
- 管理员、黑名单、白名单使用独立共享策略。

完成标准：多个房间可共享黑名单，同时保持房间本地封禁和例外；一个房间的操作不会意外影响未绑定房间。

### Phase 3：举报和证据管线

- 先实现本地举报草稿、日志截取、脱敏和证据预览。
- 接入可选中央服务，但不发布自动执行名单。
- 建立举报状态、补充证据和审核审计。

完成标准：用户上传前能准确看到证据内容；敏感配置和无关日志不会进入证据包。

### Phase 4：签名观察名单

- 中央服务发布签名、版本化的 `observed` 和 `warned` 决定。
- 本地默认只提示，支持查看理由、有效期和申诉入口。
- 完成撤销、过期、离线快照和签名失败处理。

完成标准：中央服务不可用或数据签名无效时，不扩大本地封禁范围。

### Phase 5：可选执行

- 在审核、申诉、信誉和反滥用体系稳定后，开放本地批准执行。
- 高置信度自动执行继续保持默认关闭。
- 建立误封率、撤销率、申诉处理时间等质量指标。

完成标准：每次共享封禁都可解释、可豁免、可撤销、可回滚，并有完整审计。

## 10. 当前明确不做

- 不在当前版本实现社区中央服务。
- 不按举报次数自动封禁。
- 不上传完整存档或无限范围日志。
- 不让社区服务控制管理员或白名单。
- 不要求本地系统联网才能管理房间。
- 不使用符号链接实现多房间共享。
- 不在缺少申诉和撤销能力时启用自动执行。
- 不在本阶段扩展远程节点能力。

## 11. 实施前待确认

1. 策略组是否允许包含管理员名单，还是第一版完全禁止管理员共享。
2. 安装级全局名单是否有足够价值，还是只提供策略组即可。
3. 玩家封禁原因是否允许直接同步到策略组，还是必须二次确认。
4. 社区决定的公开理由粒度和原始证据访问权限。
5. 举报者身份采用实例、运营者账号还是两者组合。
6. 中央服务的运营主体、隐私条款、证据保留期限和申诉责任。
7. 哪些行为类别能够形成结构化、可复核的服务器日志证据。
