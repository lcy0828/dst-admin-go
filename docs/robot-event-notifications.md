# 机器人事件播报

DST Admin 饥荒助手可以把房间变化直接发到已启用的群。播报由插件订阅面板记录，不需要模型判断，也不会为了补发通知而重新执行游戏操作。

## 在群里开启

先安装并连接官方统一插件，在目标群发送 `/dst 启用本群`。房间自动沿用面板授权范围，也可以用 `/dst 订阅房间 房间名称` 缩小范围。

管理员可以选择一个通知预设：

```text
/dst 通知预设 玩家群
/dst 通知预设 管理群
```

也可以逐项调整：

```text
/dst 通知 房间维护 开
/dst 通知 季节变化 开
/dst 通知 更新提醒 开
/dst 通知 备份提醒 开
/dst 通知 面板更新 开
/dst 通知 死亡复活 开
/dst 通知 Boss击杀 开
/dst 通知 模组消息 开
/dst 通知 运行告警 开
/dst 聊天播报 开
```

玩家群预设开启进退服、房间维护、季节、更新提醒、死亡复活和 Boss 击杀；管理群另外开启备份异常、管理程序更新提醒和运行告警。聊天和模组消息单独设置。升级不会自动覆盖原有开关，新增类别默认关闭。`/dst 设置` 查看当前设置，`/dst 播报 关` 关闭所有播报。

房间订阅和通知开关不会授予游戏修改权限。管理程序版本通知需要面板管理读取权限；权限不足只影响该类通知。

## 会收到什么

| 类别 | 内容 |
| --- | --- |
| 房间维护 | 单房间、批量及定时启动、停止、重启的结果；异常退出；回档、重置、恢复备份后的可确认状态 |
| 季节变化 | 主世界的实际季节变化；首次连接只建立基线，不补发当前季节 |
| 更新提醒 | 发现游戏或模组新版；游戏更新开始、安装结果和原运行世界恢复情况；模组文件准备、重启加载和失败情况 |
| 备份提醒 | 备份失败、未确认的校验结果；日常备份成功保留在记录中，默认不群发 |
| 面板更新 | 面板或节点程序发现新版、更新结果；不会把管理程序重启写成游戏重启 |
| 死亡复活 | 玩家死亡、从幽灵状态复活；只描述已采集到的事件 |
| Boss击杀 | 已识别原版 Boss 的玩家击杀记录，包含玩家与所在世界 |
| 模组消息 | 模组通过专用入口提交的简短中文消息 |
| 运行告警 | 游戏持续变慢及持续恢复；暂停、等待采样和缺失数据不会按零分告警 |

模组文件下载完成后，运行中的相关世界需要重启才能加载新版；已停止的世界在下次启动时加载。下载完成不表示游戏已经使用新版，也不保证模组兼容。

游戏新版检查复用官方发布信息和本机/Agent 的实际安装版本。有人订阅房间动态时，所有群共用检查，每 30 分钟最多一轮；无人订阅时不启动这项后台检查。测试分支、离线节点和版本读取失败不会被判成需要更新。

只有订阅“更新提醒”才会触发上述游戏新版检查。模组新版提醒依赖房间的模组自动检查；未开启时，手动检查发现的新版也会记录和播报。

## 回档和重置怎么判断

“回档 2 点”表示回退两个存档点，可能跨越多个游戏日，也可能仍在同一天。通知显示采集到的实际天数，不用参数减天数。

只有执行回执时会说明“结果待确认”。世界重新运行且读到新状态后，可以报告“第 77 天 → 第 74 天”；如果没有证据证明指定存档或新地图已载入，仍保持结果待确认。等待超过十分钟而未读到状态时，会留下等待超时记录。系统不会自动重发回档、重置或恢复操作。

恢复备份的文件结果与之后的世界状态分别记录。原来停止的世界不会仅为采集天数而被启动。

## 死亡、击杀与采集开关

死亡和复活复用已有玩家活动采集；Boss 击杀还需要活动设置中的战斗采集。关闭采集后不会产生这类新记录。群内打开播报不会改变面板的采集设置；`/dst 设置` 会提示已关闭或暂时无法读取的采集。设置状态不代表采集链路一定健康，断档期间可能缺少事件。

Boss 目前采用固定原版名单，包括独眼巨鹿、熊獾、龙蝇、麋鹿鹅、蚁狮、蜂王、毒菌蟾蜍、远古守护者、远古织影者、帝王蟹、邪天翁、天体英雄最终阶段、疯猪、恐怖之眼及双子魔眼等。通知只表示记录中归属该玩家的击杀，不是参与榜，也不保证覆盖宠物、环境或私有模组逻辑造成的击杀。未知生物不会因为带有 Boss 标签就自动加入名单；缺少实体身份时不发送击杀通知。

通知写入失败会保留活动记录上的待处理标记，在已有采集轮次中补投；数量和保存时间仍受活动记录的保留与容量限制。不会重新执行任何游戏指令，也不会在升级后自动群发全部旧活动。

## 运行告警

复用性能报表已有的有效样本：评分不高于 60，持续累计至少 90 秒且不少于三个有效样本时提醒；评分不低于 80，达到相同持续要求后提醒恢复。再次触发低分提醒至少间隔十分钟。采样频率仍使用面板性能报表的设置，较长采样间隔会让确认更晚。

暂停、无人休眠、停止、样本中断、世界运行实例变化都会打断连续判断。CPU 占用高不会单独被解释为游戏变慢。告警状态持久保存，避免面板重启后重复报同一异常。只有订阅运行告警或配置了对应通知渠道时才处理告警状态；不会另起性能采集器，也不会自动打开已关闭的性能采集。

## 模组接入消息

模组可以在服务器侧调用专用入口。兼容旧版本时先检查入口是否存在：

```lua
local runtime = rawget(_G, "DSTAdmin")
if runtime and runtime.Events and type(runtime.Events.Notify) == "function" then
    local accepted = runtime.Events.Notify(
        "example_mod", "mastery_level", "示例玩家的拓荒技能升到 2 级"
    )
    -- accepted=true 仅表示运行时接收，不能作为群消息送达凭据。
end
```

来源和事件代号各不超过 64 个 ASCII 字符，使用字母、数字、下划线、点或连字符，首字符不能是点或连字符。正文必须是有效 UTF-8 单行文本，最多 1024 字节。返回 `false` 表示入口尚未就绪、输入不合规或超出限额；不要立即循环重发。

每个世界每分钟最多接收 20 条、每个来源最多 5 条、最多 8 个来源；面板再次限流并去重。入口不接受 Lua、函数或通知类别，只处理文本，不能触发管理操作。群需单独开启“模组消息”，地面和洞穴均可使用。消息沿用现有 Runtime 事件窗口，长时间断线可能丢失；不承诺每条都送达。旧 Runtime 没有该入口，需通过面板既有运行时更新能力升级，无需为此重启世界。

## 最近动态和自定义文字

直接对机器人说“最近动态”“1服最近发生了什么”或“最近更新记录”，插件直接查询面板已有记录。记录不完整不代表事情没发生。

使用 `/dst 模板` 编辑对应通知模板，也可以在插件配置中编辑各类事件模板（包括死亡复活、Boss 击杀、模组消息和运行告警）。模板必须保留正文 `{body}` 和结果 `{result}`；不支持脚本、表达式或网络访问。

## 断线、重复和兼容

- 首次开启从当前记录位置开始；重连按保存的位置补读。读取位置与待发消息一起保存。
- 同一事件在同一群去重，不同群独立保存投递结果。旧倒计时不补发；十分钟前的维护和更新结果汇成历史摘要，超过一天的记录不再群发。死亡、击杀、模组消息和运行告警超过十分钟不再群发，以免被误当成当前事件。
- 插件能关联到本群提交的同一任务时，任务回执与主动结果通知共用投递记录，避免重复发送完成结果。
- 待发维护结果最多保留一天；聊天保持短时有效。队列有上限，积压时优先丢弃聊天。
- QQ 发送超时可能已经送达，插件记录“投递结果不确定”并避免自动重发。此时不能保证每条通知都送达，可查面板最近动态。
- 每次发送前重新检查当前群、房间和类别授权。房间权限撤回后，不继续发送旧的待发内容。
- 新插件连接旧面板时，插件先读取 `supportedKinds`，缺少的新类别显示为暂不可用；原有进退服与聊天继续按已有能力工作。旧插件连接新面板仍使用原入口。
- SSE 每分钟重连并重新鉴权；不支持流的客户端可用增量读取。记录保留最近 30 天、最多 10,000 条，超出范围会明确标记历史缺口。

## API / MCP 接入

房间读取权限可使用：

| MCP 工具 | 用途 |
| --- | --- |
| `api_readRoomNotificationEvents` | 按房间增量读取，持久保存 `nextCursor` |
| `api_streamRoomNotifications` | 获得该房间的实时事件订阅地址 |
| `api_listRoomRecentEvents` | 查询最近已记录的动态 |

首次订阅示例：

```json
{
  "path": {"roomId": "example-room"},
  "query": {"tail": true, "limit": 50}
}
```

随后读取：

```json
{
  "path": {"roomId": "example-room"},
  "query": {"after": "上次返回的 nextCursor", "limit": 50}
}
```

结果示例（合成数据）：

```json
{
  "items": [{
    "id": "example-operation-result",
    "schemaVersion": 1,
    "kind": "world.change",
    "category": "maintenance",
    "roomId": "example-room",
    "title": "回档后世界状态",
    "message": "世界已重新运行：第 77 天 → 第 74 天。目标存档结果仍待确认。",
    "status": "uncertain",
    "severity": "warning",
    "occurredAt": "2026-01-01T00:00:00Z",
    "facts": {"action": "rollback", "beforeDay": 77, "day": 74}
  }],
  "nextCursor": "由服务端返回的读取位置",
  "hasMore": false,
  "historyTruncated": false,
  "retentionDays": 30
}
```

SSE 的 `notice.page` 携带同样的结果，事件 ID 为 `nextCursor`，重连时放入 `Last-Event-ID`。房间游标绑定房间及过滤条件，不能换房间或混用全局通知。`supportedKinds` 是该面板支持的事件类型，插件先核对后订阅；旧面板不返回时仅使用原有类别。`collection` 是已保存的采集开关，`enabled` 不保证记录完整。接收端应忽略未知的新增字段、事件类别和版本；不要把未知状态显示为成功。

`api_readNotificationEvents` 继续是管理范围入口，不向房间只读用户开放全局记录。MCP 本身不会主动给群发消息，持续接收和投递由插件负责。
