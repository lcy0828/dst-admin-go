# 游戏通知功能说明

## 页面用途

“游戏通知”只管理真实发送到 DST 游戏内的消息，不再维护没有投递能力的后台公告。

- 即时通知：优先从运行中的主分片执行一次 `c_announce`，由 DST 转发到相连分片；主分片未运行时选择其他运行分片。
- 操作前提醒：停止、重启、停服备份、游戏更新和 Mod 重启生效前按房间策略倒计时。
- 自动化通知：定时任务使用 `notification.send`，并进入同一发送历史。
- 发送历史：查看公告内容、整个房间的广播结果和发送世界；展开后可查看各世界的记录与运行机器。

## 发送结果

| 页面显示 | 含义 |
| --- | --- |
| 正在发送 | 正在检查可用世界并提交公告；单次广播最多等待 8 秒游戏确认。 |
| 已提交 | 已提交到控制台，但没有游戏执行回执。没有回执的旧版成功记录也按此显示。 |
| 游戏已执行 | 收到了与本次公告对应的游戏执行回执。 |
| 结果未确认 | 没有取得有效回执，公告可能已经发出；不会自动重发。 |
| 发送失败 | 已确认本次发送或游戏执行失败，可展开查看原因。 |

房间广播只通过一个世界发送，优先选择地面，其次选择其他运行世界。发送尝试开始后，不会再换到另一个世界重复发送。其余世界显示“无需重复发送”或“未重复尝试”，与发送前发现的“世界未运行”分别记录。游戏执行确认不代表每位玩家都已收到；断开连接的世界不保证能收到游戏转发。

本机和 Agent 共用现有 Runtime 执行与回执通道，不增加后台轮询。游戏 Runtime 不可用时显示失败，执行后的回执超时显示“结果未确认”；不会为公告自动重启世界或重放消息。

自动化的“发送游戏通知”每轮只尝试一次，即使旧任务配置了失败重试，也不会再次发送同一轮公告。回执丢失或发送后记录保存失败时，重复执行可能让玩家收到多条公告；请先查看记录和游戏消息，再决定是否手动重新发送。其他自动化动作保留原有重试设置。

## 倒计时行为

- 默认开启，默认提前 30 秒，可配置 10-600 秒；页面提供 15、30、60、120、300、600 秒选项。
- 在起始时间、30 秒和 10 秒节点中发送适用的提醒。
- 维护前即时查询各运行分片的游戏在线名单，按玩家 ID 去重；确认无人时不公告、不等待。暂停不等于无人，数据库旧人数不参与判断。
- 人数查询失败时明确显示“无法确认”，按房间策略保留通知等待。
- 停止/重启确认弹窗显示本次在线人数、通知设置，并提供“立即执行”；该入口只跳过本次通知与等待，不更改策略。执行时再次读取人数，避免把弹窗打开时的空服结果沿用到稍后的操作。
- 定时玩家采集在暂停时仍合并日志中的最后离线事件，保持人物属性的原始采样时间。
- 多房间游戏更新使用一条统一时间线，不会按房间串行累加等待时间。
- 停服备份也使用此策略，来源记录为 `backup`。不停服备份、全房间已停止时不发停服公告；更新或模组操作的保护备份由外层操作提醒，避免重复倒计时。
- 投递失败会记录但不会阻止维护；取消 Job 会同时取消倒计时和后续操作。

## 部署与分片

投递通过各世界实际分配的运行机器完成，本机、Agent 和混合部署使用同一行为。广播尝试开始后，不再逐个检查其余世界状态，也不把它们当作独立投递失败。发送前已确认停止的世界会单独记录原因。

## API

```text
GET  /api/v2/game-notifications
POST /api/v2/game-notifications
GET  /api/v2/rooms/:roomId/game-notification-policy
PUT  /api/v2/rooms/:roomId/game-notification-policy
GET  /api/v2/rooms/:roomId/maintenance-preview
```

旧 `/api/v2/announcements` 路由不再注册。旧公告代码和表仅暂留用于识别历史数据，不参与新功能。

API / MCP 调用 `sendGameNotification` 后应通过 `listGameNotifications`，按返回任务的 `jobId` 找到发送记录，读取 `outcome`。`confirmed` 才表示游戏已执行，`submitted` 仅表示提交，`unconfirmed` 表示可能已执行，不能自动重发。任务成功和旧字段 `successCount` 均不代表玩家收到了公告。`skipReason` 区分 `world_stopped`、`room_broadcast`、`broadcast_attempted`。这些为兼容新增字段，旧记录保留；不会把旧的“成功”补成游戏执行确认。
