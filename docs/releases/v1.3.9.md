修复启动和定时重启丢失 LuaJIT 模式、跨分片热备份失败，并统一日志规则管理与后台版本检查。

- **运行模式继承（#26）：** 普通启动沿用各世界上次成功使用的方式，重启保留当前实际方式；Master、Caves 可以分别使用原版、LuaJIT 或 Arena GC。选择成功后持久保存，管理服务重启不会丢失。页面、批量操作、OpenAPI、MCP 和定时任务使用同一套规则；定时启动和重启也可明确指定 `parameters.runtimeMode`。新世界无历史时使用原版，安装 LuaJIT 不会自动切换现有世界。
- **启动检查与结果：** 世界状态旁显示实际或下次启动方式，可从操作菜单选择方式并启动或重启。重启在停止世界前检查模式兼容性，节点离线、模式未知或包不可用会明确提示，不会静默切回原版。任务重试保留原模式，部分失败不覆盖其他世界的偏好；普通停止仍可执行，模式无法记录时给出提醒。
- **跨分片热备份：** 修复定时备份误接收普通自动存档、导致 Master 与 Caves 快照不一致而报 `cross-shard snapshot barrier failed` 的问题。各分片先准备，再按同一目标执行保存，并核验归档中的实际快照；遇到冲突进行有限重试。失败和取消时有界释放保存保护，页面和通知区分主要失败阶段、未生成文件与真正的归档损坏。
- **全局日志规则：** 所有房间共用一套解析规则，不再要求逐房间重复配置；保留旧接口兼容和旧规则迁移预览。修改后在下次刷新对应房间日志时生效，不主动触发全量解析。
- **后台新版检查：** 未配置过检查间隔时默认每 **30 分钟**检查一次，已有自定义间隔保留，可在软件更新设置中调整。检查独立于页面访问；启用对应新版通知的邮箱或 Webhook 渠道可接收通知，MCP 客户端可通过自己的 Webhook 接收端对接。仅接入 MCP 不会自动获得推送，后台检查也不会自动安装更新。

**升级：** 在 **系统设置 → 软件更新** 更新控制端，独立 Agent 在 **机器管理** 中更新，建议两端一并升级。前端已内嵌，Runtime 升至 **2.4.18**。已运行的世界通过现有 Runtime 更新机制应用新版，旧 Agent 或未就绪的 Runtime 会明确报出能力不足，不伪报热备份成功。Docker 用户也可拉取 `v1.3.9` 或 `latest` 后重建容器；国内推荐阿里云镜像，其他地区使用 Docker Hub。升级保留配置、数据库与游戏存档。升级前已经丢失启动模式历史的停止世界，首次启动请手动选择一次。

Fixes lost LuaJIT selections during starts and scheduled restarts, synchronizes hot backups across shards, and unifies log rules and background release checks.

- **Runtime inheritance (#26):** start uses each world's last confirmed choice; restart preserves its actual runtime. Master and Caves can retain different modes. Choices survive management-service restarts. UI, batch actions, OpenAPI, MCP and automation share these rules; scheduled start/restart also accept optional `parameters.runtimeMode`. New worlds without history use Game Lua. Installing LuaJIT does not switch existing worlds automatically.
- **Validation and reporting:** show actual or next-start runtime beside world status, with optional menu actions to change it. Validate compatibility before stopping worlds for a restart. Report offline nodes, unknown modes and unavailable packages instead of silently falling back. Retries retain their resolved mode and partial failures do not replace other choices. Stop remains available, with a warning when the previous mode cannot be remembered.
- **Cross-shard hot backups:** ordinary autosaves no longer satisfy the managed backup barrier. Prepare every shard, arm a shared save target, verify the actual archived snapshot, and retry conflicts within fixed limits. Failures and cancellation release protection within bounded deadlines. UI and notifications distinguish failure phases, ungenerated files and corrupt archives.
- **Global log rules:** all rooms share one rule set. Preserve compatibility routes and legacy migration previews. Changes apply on the next log refresh without eagerly reparsing every room.
- **Background release checks:** the default interval is **30 minutes** for installations without a saved value; existing custom intervals remain unchanged. Checks run independently of page visits and remain configurable. Enabled release email/Webhook channels can receive notifications. External MCP clients need their own Webhook receiver for push delivery; MCP access alone does not subscribe them. Checks never install updates automatically.

**Upgrade:** update the Controller under **System settings → Software updates** and standalone Agents under **Machines**; updating both is recommended. The frontend is embedded and Runtime is **2.4.18**. Running worlds use the existing Runtime update mechanism. Older Agents or unavailable Runtime capabilities produce explicit errors instead of false backup success. Docker users may pull `v1.3.9` or `latest` and recreate containers. Use Alibaba Cloud mirrors in mainland China or Docker Hub elsewhere. Configuration, databases and game saves are preserved. For stopped worlds whose earlier runtime choice was already lost, select it once on the first start after upgrading.
